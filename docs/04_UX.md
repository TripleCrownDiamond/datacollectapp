# 04 — Expérience utilisateur

## 1. Principes directeurs

1. **Le terrain dicte tout.** Cibles tactiles larges (min 48 dp), contrastes élevés lisibles en plein soleil, actions principales accessibles au pouce, tolérance aux gestes imprécis (gants, pluie).
2. **Zéro perte, zéro angoisse.** L'utilisateur sait toujours ce qui est sauvegardé, ce qui est synchronisé, ce qui reste à faire. Aucune action ne peut détruire une saisie sans confirmation explicite.
3. **Le chemin heureux en un minimum de gestes.** Ouvrir l'app → nouvelle soumission du dernier formulaire utilisé : 2 taps.
4. **Progressivité.** Les fonctions avancées (SIG, IA, logique) n'alourdissent jamais le parcours de base ; elles apparaissent quand elles sont configurées.
5. **Statuts honnêtes.** Jamais de spinner infini : chaque attente affiche progression, cause et action possible (réessayer, passer en wifi, continuer hors ligne).

## 2. Offline-first : règles UX

- L'état réseau est visible en permanence (icône discrète), mais **l'app ne se comporte jamais différemment** hors ligne pour la collecte : mêmes écrans, mêmes fonctions.
- Toute fonctionnalité indisponible hors ligne (ex. génération IA) est masquée ou grisée avec l'explication « Disponible avec connexion », jamais une erreur après coup.
- La synchronisation est **automatique par défaut** (au retour du réseau, à l'ouverture de l'app) et toujours déclenchable manuellement. Options : wifi seulement, médias différés.
- Statuts de soumission, avec code couleur constant partout : `Brouillon` (gris), `Finalisée — en attente` (orange), `Envoi en cours` (bleu, avec %), `Synchronisée` (vert), `Rejetée` (rouge, avec motif).
- En cas d'échec de sync : retry automatique avec backoff, message clair (« Sera réessayé automatiquement »), jamais de perte ni d'action requise en urgence.

## 3. Parcours critiques et budgets d'interaction

| Parcours | Budget | Notes |
|---|---|---|
| Ouvrir l'app → commencer une soumission | ≤ 2 taps, < 3 s | Raccourci « dernier formulaire » sur l'accueil |
| Répondre à une question simple | ≤ 2 gestes | Passage auto au champ suivant optionnel |
| Capturer une photo conforme | ≤ 3 taps | Compression silencieuse en arrière-plan |
| Capturer un point GPS précis | ≤ 2 taps + attente visible | Jauge de précision en temps réel, seuil affiché |
| Finaliser + mettre en file | ≤ 2 taps | Récapitulatif des erreurs éventuelles avant finalisation |
| Web : créer un formulaire 20 questions | < 30 min sans formation | Mesuré en test utilisateur |

## 4. Navigation

**Mobile** — barre d'onglets : `Accueil` (projets/formulaires, reprise rapide), `Carte`, `Envois` (file + historique), `Paramètres`. Le remplissage de formulaire est un flux plein écran modal : une question ou un groupe par écran (mode « pas à pas », défaut) ou liste déroulante complète (mode « grille », au choix de l'utilisateur), barre de progression, sommaire accessible pour naviguer entre sections.

**Web** — barre latérale par projet : `Vue d'ensemble` (dashboard), `Formulaires`, `Soumissions`, `Carte`, `Équipe`, `Paramètres` ; sélecteur d'organisation et de projet en haut. Le form builder est un espace dédié 3 panneaux (palette / canevas / propriétés) avec aperçu mobile.

## 5. Navigation dans les formulaires

La navigation entre sections doit être **extrêmement simple** — utilisable sans avoir lu de manuel ([P3](17_PRINCIPES_CONCEPTION.md)). Le système propose systématiquement :

- **progression visuelle par étapes** et **barre de progression** (part du formulaire complétée) ;
- **navigation précédent/suivant** et **accès rapide à n'importe quelle section** (sommaire) ;
- **aperçu global** de l'état des sections (terminée / en cours / non commencée / avec erreurs) ;
- **reprise automatique** à la dernière section visitée à la réouverture d'un brouillon ;
- **passage temporaire d'une section** si les règles du questionnaire l'autorisent (marquée « à compléter ») ;
- **recherche dans un long questionnaire** (par libellé de question ou de section) ;
- **validation en temps réel** : les erreurs et incohérences sont signalées pendant la saisie, pas à la fin.

## 6. Ergonomie de saisie

- Clavier adapté au type (numérique, email, date native) ; unités affichées dans le champ.
- Erreurs de validation **à la sortie du champ**, en langage clair, sous le champ — jamais de popup bloquante.
- Logique conditionnelle : les questions apparaissent/disparaissent avec une animation brève ; les réponses des questions masquées sont conservées en brouillon mais exclues à la finalisation (règle du form-engine).
- Calculs et indicateurs mis à jour **instantanément** à chaque saisie (superficies, sommes, compteurs — voir [18_XLSFORM §4](18_XLSFORM.md)).
- Sauvegarde automatique continue ; l'indicateur « Enregistré » est visible après chaque modification.

### Groupes répétables

Les groupes répétables (plantations, membres du ménage, activités économiques, animaux, parcelles…) doivent être **faciles à gérer**. Présentés comme une **liste claire de toutes les occurrences** (carte par occurrence, résumé de l'occurrence, compteur). L'utilisateur peut :

- **ajouter** une occurrence ;
- **modifier** une occurrence ;
- **dupliquer** une occurrence (repart de la précédente) ;
- **supprimer** une occurrence (avec confirmation) ;
- **voir toutes les occurrences** d'un coup d'œil, avec leur état (complète / incomplète).

## 7. Accessibilité

- **Cible : WCAG 2.1 AA** sur le web ; équivalent mobile (TalkBack/VoiceOver fonctionnels sur tout le parcours de collecte).
- Contraste ≥ 4,5:1 texte, ≥ 3:1 composants ; jamais la couleur seule comme vecteur d'information (statuts = couleur + icône + libellé).
- Navigation clavier complète sur le web (form builder inclus) ; focus visible.
- Tailles de police respectant les réglages système (Dynamic Type / font scale) jusqu'à 200 %.
- Libellés multilingues FR/EN ; formulaires multilingues avec bascule de langue en cours de saisie.

### Internationalisation réelle (au-delà de FR/EN)

La collecte terrain est mondiale, majoritairement Sud : prévoir dès l'architecture (pas en rattrapage) — le RTL et la pluralisation sont des contraintes de layout, pas de simples traductions.

- **RTL (arabe, etc.)** : miroir complet de la mise en page (direction, alignements, icônes directionnelles, sens de progression du formulaire). Utiliser les propriétés logiques CSS (`margin-inline`, `text-align: start`) et `I18nManager` côté RN dès le départ ; tester au moins une langue RTL en continu.
- **Langues cibles prioritaires après FR/EN** : arabe, espagnol, portugais, swahili — architecture i18n extensible (next-intl web, i18next mobile), pluralisation ICU, formats de date/nombre localisés.
- **Formulaires multilingues** : le contenu (labels, options, messages) est traduisible par formulaire ([13_DESIGN_SYSTEM §9](13_DESIGN_SYSTEM.md)) ; l'IA peut pré-traduire (AI-05) mais l'humain valide.
- **Longueur variable** : les traductions allongent le texte (allemand, +30 %) — layouts tolérants, jamais de largeur fixe sur les libellés.

Reste une contrainte transverse ([24_RISQUES_ET_LACUNES R9](24_RISQUES_ET_LACUNES.md)) : le RTL touché tardivement coûte un refactor UI — d'où sa prise en compte dès la V0 côté architecture, même si peu de langues sont livrées au départ.

## 8. Métriques UX suivies

| Métrique | Définition | Cible V1 |
|---|---|---|
| Temps moyen de soumission | finalisation − ouverture, médiane par formulaire | −30 % vs outil précédent |
| Taux d'abandon de saisie | brouillons jamais finalisés / soumissions commencées | < 10 % |
| Taux d'erreur à la finalisation | finalisations bloquées par validation / tentatives | suivi (baseline) |
| Délai de première valeur | inscription → premier formulaire publié | < 1 h |
| Taux de sync sans intervention | soumissions synchronisées sans action manuelle | > 95 % |
| Crash-free sessions mobile | sessions sans crash | > 99,5 % |

Ces métriques sont instrumentées dès la V1 (événements anonymisés, opt-out par organisation, conformité RGPD).

## 9. Optimisation terrain (checklist de conception)

- [ ] Utilisable à une main, en marchant, en plein soleil.
- [ ] Fonctionne sur Android 2 Go RAM sans saccade (listes virtualisées, images lazy).
- [ ] Consommation batterie maîtrisée : GPS activé seulement pendant la capture ; pas de wake-locks permanents.
- [ ] Stockage maîtrisé : compression des médias, purge configurable des soumissions synchronisées (défaut : conserver 30 j).
- [ ] Aucune dépendance à Google Play Services pour les fonctions cœur (cartes via MapLibre, localisation via API standard).
