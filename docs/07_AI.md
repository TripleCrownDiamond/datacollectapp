# 07 — Intelligence artificielle

Spécification de la couche IA. Principe cardinal (règle métier n° 8 du [PRD](02_PRD.md)) : **l'IA propose, l'humain valide**. Aucune écriture directe en production, aucun appel IA dans le chemin critique de collecte ou de synchronisation — tout est asynchrone et dégradable (la plateforme fonctionne intégralement sans clé IA configurée).

## 1. Architecture

- Module NestJS `ai` dans `apps/api` — **seul point de contact** avec le fournisseur (les clients web/mobile n'appellent jamais l'IA directement ; pas de clé côté client).
- Fournisseur : **API Claude (Anthropic)**. Modèles configurables par tâche via env : défaut `claude-sonnet-5` (génération, analyse), `claude-haiku-4-5-20251001` (tâches courtes : traduction, classification) — centralisés dans une config unique `ai.config.ts`.
- Exécution en **jobs asynchrones** (table `ai_jobs`, worker BullMQ/Redis) : le client crée un job (`POST /ai/...`), poll ou reçoit le résultat (`GET /ai/jobs/:id`). Timeout, retry (2), coût tokens journalisé par job.
- **Sorties structurées** : chaque tâche définit un schéma zod de sortie (dans `packages/shared`) ; la réponse du modèle est parsée et validée — une sortie invalide = 1 retry avec l'erreur en contexte, puis échec propre du job.
- **Garde-fous données** : les données de soumissions envoyées à l'IA sont minimisées (champs nécessaires uniquement) ; option par organisation « désactiver l'IA » et « exclure les champs marqués sensibles » ; journal des appels dans l'audit log ; aucune donnée conservée pour entraînement (API commerciale, opt-out par défaut).

## 2. Cas d'usage

### AI-01 — Génération de formulaires (V1)
**Sources d'entrée acceptées** : (a) **description en langage naturel** ; (b) **questionnaire Word** (.docx) ; (c) **PDF** ; (d) **XLSForm** (déterministe, sans IA — voir [18_XLSFORM §6](18_XLSFORM.md)). Pour (b) et (c), l'IA extrait la structure du questionnaire (questions, types probables, sections, listes de choix) et la convertit en `FormSchema` ; le résultat est toujours un **brouillon à valider**.
**Entrée** : source ci-dessus + langue(s) cible(s) + contexte (secteur, éventuel formulaire existant).
**Sortie** : `FormSchema` complet (schéma JSON de [10_DATABASE.md §5](10_DATABASE.md)) validé par `form-engine` : sections, questions typées, options, contraintes plausibles, logique conditionnelle, libellés multilingues si demandé.
**Contraintes** : résultat inséré comme **brouillon** dans le builder, questions marquées « générée par IA » ; validation form-engine obligatoire avant insertion (schéma invalide = retry puis message d'erreur) ; latence cible < 60 s.
**Prompt (structure)** : system = rôle d'expert en conception d'enquêtes + spécification complète du format FormSchema + règles (noms de variables slug anglais, libellés dans la langue demandée, contraintes réalistes, pas plus de N questions sauf demande) ; user = description + contexte. Sortie via tool use / JSON forcé.

### AI-02 — Amélioration de formulaire (V2)
Analyse d'un FormSchema existant → suggestions typées (question manquante, contrainte absente, reformulation ambiguë, problème de logique, traduction manquante), chacune avec justification et patch applicable en un clic dans le builder.

### AI-03 — Contrôle qualité (temps réel à la saisie + post-sync) (V2)
Le contrôle qualité s'exerce **pendant la collecte** (analyse en temps réel des réponses, sur l'appareil pour les vérifications légères, via l'assistant IA en ligne pour les analyses sémantiques) **et** en lot post-synchronisation côté serveur. Détections visées :

- **fautes d'orthographe** (champs texte libre) ;
- **incohérences** entre réponses (ex. « âge 8 ans » + « profession : médecin ») ;
- **réponses improbables** et **valeurs extrêmes** (outliers statistiques) ;
- **doublons** (voir AI-04) ;
- **coordonnées GPS suspectes** (précision faible, saut de position, mock location, hors zone) ;
- **photos floues** (détection de netteté sur l'appareil — variance du Laplacien — avant même l'IA) ;
- **réponses incomplètes** (champs importants laissés vides).

Combinaison **règles déterministes** (rapides, hors ligne) et **analyse LLM** (sémantique). L'IA **propose une correction mais ne modifie jamais automatiquement une réponse sans validation de l'agent** ([P6/P7](17_PRINCIPES_CONCEPTION.md)). Sortie : `quality_flags` par soumission (type, sévérité, explication, suggestion) — affichés en temps réel côté mobile et dans la table web (filtre « à vérifier »). L'approbation reste humaine.

### AI-04 — Détection de doublons (V2)
Pipeline déterministe d'abord (distance GPS < seuil, egalité/similarité de champs clés par trigrammes), LLM en arbitrage sur les cas ambigus. Sortie : paires candidates avec score, écran de revue côté web (fusionner/ignorer).

### AI-05 — Traduction (V2)
Traduction des libellés d'un FormSchema vers une langue cible, en préservant variables et structure ; chaque libellé marqué « traduction auto » jusqu'à validation.

### AI-06 — Résumé IA (V2)
Synthèse en langage naturel d'un lot filtré de soumissions (période, formulaire) : tendances, points saillants, anomalies. Toujours accompagné des chiffres sources (calculés par SQL, pas par le LLM — voir §3).

### AI-07 — Chat avec les données (V3)
Question en langage naturel → réponse chiffrée + graphique. Architecture **text-to-SQL contraint** : le LLM génère une requête sur des **vues en lecture seule** du projet (jamais les tables brutes), exécutée avec un rôle SQL restreint (SELECT only, timeout 5 s, limite de lignes) ; le résultat est reformulé et affiché avec la requête inspectable. Les chiffres viennent toujours de l'exécution SQL, jamais du modèle.

### AI-08 — Rapports IA (V3)
Modèle de rapport (sections définies par l'utilisateur ou modèle bailleur) + données agrégées → document structuré (Markdown → PDF/DOCX) mêlant chiffres calculés, graphiques générés et narratif IA clairement identifiable. Relecture humaine avant tout partage.

### AI-09 — Assistant IA de terrain (V2)
Pendant la collecte, l'agent **dialogue** avec l'IA sur le questionnaire en cours (fonction en ligne, dégradable). Exemples : « Ai-je oublié une question ? », « Pourquoi cette réponse est-elle incohérente ? », « Résume ce questionnaire », « Vérifie la cohérence des superficies ». Contexte fourni au modèle : le FormSchema et les réponses courantes (minimisées, champs sensibles exclus si configuré). L'IA propose des vérifications et des corrections ; l'agent reste seul décideur. UI mobile : [05_MOBILE §2.5b](05_MOBILE.md).

### AI-10 — Analyse prédictive (IA+)
Détection d'anomalies inter-projets, recommandations d'échantillonnage, alertes précoces. Spécifié au moment de la version IA+ ; démarre par des statistiques simples et honnêtes ([15_INNOVATIONS](15_INNOVATIONS.md)).

## 3. Règles anti-hallucination

1. **Aucun chiffre inventé** : toute statistique présentée à l'utilisateur provient d'un calcul SQL/déterministe ; le LLM ne fait que formuler et interpréter.
2. **Sorties structurées validées** (zod) — jamais de parsing de texte libre.
3. **Traçabilité** : chaque artefact IA (question générée, flag qualité, résumé) est marqué comme tel dans l'UI et lié à son `ai_job`.
4. **Périmètre fermé** : les prompts interdisent explicitement d'inventer des données absentes du contexte fourni.

## 4. Coûts et quotas

- Journalisation par job : tokens in/out, modèle, coût estimé → table `ai_jobs` ; agrégats par organisation.
- Quotas par plan (configurable) : ex. V1 free = 20 générations de formulaires/mois ; dépassement = message clair, jamais de dégradation silencieuse.
- Optimisations : prompt caching sur les préambules stables (spec FormSchema), batch pour le contrôle qualité, Haiku pour les tâches courtes.

## 5. Tests

- Fixtures de descriptions → assertions structurelles sur les FormSchemas générés (types présents, logique valide, langue correcte) — tolérantes au non-déterminisme (propriétés, pas d'égalité exacte).
- Tests des garde-fous : sortie invalide simulée → retry → échec propre ; clé absente → fonctionnalités IA masquées, zéro erreur ailleurs.
- Éval périodique (script) sur un jeu de 20 descriptions de référence avec scoring automatique (validité form-engine, couverture du besoin) pour détecter les régressions de prompt.
